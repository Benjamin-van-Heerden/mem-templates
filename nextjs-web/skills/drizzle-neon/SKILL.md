# Drizzle and Neon

- Drizzle ORM with `node-postgres` (`pg`) on Neon. One Neon project per app: branch `dev` for development, `main` for production. There is no local Postgres.
- The schema lives in `src/db/schema/*.ts` and is re-exported from `src/db/schema/index.ts`.
- `src/db/client.ts` exports `db` and the `Db`/`Tx` types repositories take. It imports `server-only`, so only server code can reach the database.
- Every query lives in `src/db/repositories/<entity>.ts` (see Repositories).
- SQL migrations live in `drizzle/`, generated by drizzle-kit and committed.

## Connections

Neon provides two URLs for the same database:

- `DATABASE_URL`: pooled (PgBouncer, transaction mode), used by the app.
- `DATABASE_URL_UNPOOLED`: direct, used by migrations, `drizzle-kit`, dumps and anything that needs session state (`SET`, session advisory locks, `LISTEN/NOTIFY`).

`postgresUrl` in `src/env/schema.ts` rewrites Neon's `sslmode=require` to `sslmode=verify-full` when the app reads the URL: node-postgres already treats `require` as `verify-full` but warns that this will change, and `.env.local` keeps Neon's form for `psql` and the `neon` CLI.

Over the pooled URL, session state does not survive the transaction. Use `pg_advisory_xact_lock` inside a transaction, not `pg_advisory_lock`. Locally both variables point at the same database.

The client keeps a small pool per function instance and calls `attachDatabasePool(pool)` from `@vercel/functions`, so Vercel Fluid compute closes idle connections before suspending an instance:

```ts
const pool = globalForDb.pool ?? new Pool({ connectionString: serverEnv.DATABASE_URL, max: 5, idleTimeoutMillis: 5000, connectionTimeoutMillis: 10000 })
attachDatabasePool(pool)
export const db = drizzle(pool, { schema, casing: 'snake_case' })
```

## Schema

- One file per domain (`auth.ts`, `notes.ts`, ...). `auth.ts` is generated by better-auth; do not edit it by hand (see `better-auth`).
- `casing: 'snake_case'` is set in both `drizzle.config.ts` and the client, so write camelCase keys and leave out column names: `createdAt: timestamp({ withTimezone: true })` becomes `created_at`.
- IDs: `uuid().primaryKey().defaultRandom()` for app tables. better-auth's tables use text IDs, so foreign keys to `user.id` are `text()`.
- Always `timestamp({ withTimezone: true })`, and `.notNull().defaultNow()` for creation times.
- Declare foreign keys with an explicit `onDelete`. Index the columns you filter and sort on together, for example `index().on(t.userId, t.createdAt)`.
- Put constraints (`notNull`, `unique`, `check`) in the schema, not only in zod.

## Repositories

All queries live in `src/db/repositories/<entity>.ts`, one module per table or aggregate (`notes.ts`, `users.ts`). They are the only code that builds SQL; the rest of the app calls their functions.

```ts
// src/db/repositories/notes.ts
import 'server-only'
import type { Db } from '@/db/client'
import { note } from '@/db/schema'

export type Note = { id: string; body: string; createdAt: Date }

export async function listForUser(db: Db, userId: string, limit = 50): Promise<Note[]> {
  return db.select({ id: note.id, body: note.body, createdAt: note.createdAt }).from(note).where(eq(note.userId, userId)).orderBy(desc(note.createdAt)).limit(limit)
}
```

- Plain exported functions, imported as a namespace: `import * as notesRepo from '@/db/repositories/notes'`, then `notesRepo.listForUser(db, user.id)`.
- The first argument is always `db: Db`, the pool or a transaction (`Db` and `Tx` come from `src/db/client.ts`). A repository never imports `db` and never opens a transaction: the caller decides what runs together.
- Name functions for what they mean in the domain (`listForUser`, `countSince`, `markPaid`) rather than wrapping each Drizzle call. A query used once still belongs here.
- Return narrow types declared in the module, selecting only the columns callers need.
- No auth, caching, `next/*` imports or request data. Repositories trust their arguments, so callers pass the id from `getCurrentUser()`, never one sent by the client.

Callers own everything else:

| Caller | Owns | Passes |
| --- | --- | --- |
| `src/features/<domain>/data.ts` | the auth check, `use cache` and tags | `db` |
| Server Actions (`actions.ts`) | auth, zod validation, `updateTag` | `db`, or `tx` for writes that belong together |
| Route Handlers | auth or the cron secret | `db` |
| Workflow steps (`<name>-steps.ts`) | idempotency; there is no session, ids come from the workflow | `db` or `tx` |

```ts
// a Server Action whose writes succeed or fail together
await db.transaction(async (tx) => {
  const invoice = await invoicesRepo.create(tx, { customerId, total })
  await paymentsRepo.allocate(tx, invoice.id, total)
})
```

Pages and components never import `@/db/*`: they read through a feature's `data.ts` and write through its Server Actions.

The exceptions are `src/db/` itself, `src/features/auth/server.ts` (it hands `db` and the schema to better-auth's adapter), and the seed: `scripts/` and `syncSuperAdmin` run raw SQL on their own unpooled connection. `no-restricted-imports` in `eslint.config.mjs` enforces the rest: outside those, nothing imports `drizzle-orm` or `@/db/schema`, and no `.tsx` file imports `@/db/*`.

## Queries

Inside repositories:

- Use the query builder (`db.select().from(...)`) for most reads, and `db.query.<table>.findMany({ with })` for nested relations. Select only the columns the caller needs.
- User-scoped functions take the user's id as an argument and always filter by it.
- Writes that must succeed or fail together run in `db.transaction(async (tx) => ...)`, opened by the caller, with `tx` passed to every repository call inside.
- Guard against duplicate work (a double-submitted form, a retried workflow step) with unique constraints plus `onConflictDoNothing`/`onConflictDoUpdate`, or a `pg_advisory_xact_lock` inside the transaction.
- Paginate lists (`limit` plus a cursor on an indexed column). Never load unbounded tables.
- Raw SQL only through the `sql` template tag, which parameterises values.

## Migrations

Workflow for a schema change:

1. Edit `src/db/schema/*.ts`.
2. `bun run db:generate` writes a SQL migration to `drizzle/`. Read it: renames often come out as a drop plus an add.
3. `bun run db:migrate` applies it locally.
4. Commit the schema and the migration together.

Deployments migrate themselves: `"build": "bun scripts/migrate.ts && next build"`. The script uses the unpooled URL, takes a session advisory lock so concurrent builds wait instead of racing, and applies pending migrations with Drizzle's migrator. It is a no-op when nothing is pending.

Because the database is migrated before the new code is live, and a failed build can leave it ahead of the running code, **migrations must be additive**:

- Add a table, a column (nullable or with a default) or an index: one deploy.
- Rename or retype a column: add the new column, write to both, backfill, switch reads, then drop the old one in a later deploy.
- Drop a column or table: first deploy code that no longer uses it, then drop it in a later deploy.
- Backfills of any size belong in a script or workflow, not in the migration.

Never run `drizzle-kit push` against a shared database; it applies changes without a migration file. It is fine against a throwaway Neon branch.

## Seed

`scripts/seed.ts` runs after the migrations in every build (`bun scripts/migrate.ts && bun scripts/seed.ts && next build`) and by hand with `bun run db:seed`. It runs in one transaction over the unpooled URL and must stay idempotent, because it runs against the same database on every deploy:

- It keeps the one super admin in sync with `SUPER_ADMIN_*` (see `better-auth`).
- Reference data goes below that call, written as upserts (`insert … on conflict do update`), never as plain inserts.
- Bulk or one-off data changes are scripts run by hand (`bun scripts/<name>.ts`) or workflows, not seed code.

## Environments and the Neon CLI

- **development**: the Neon branch `dev`, shared by the team. Its URLs are in each developer's `.env.local`. A developer who needs isolation branches from `dev` (`neon branches create --project-id <id> --name dev-<name> --parent dev`) and points their `.env.local` at it.
- **production**: the Neon branch `main`, with its URLs in Vercel's Production environment. Every production build migrates and seeds it.
- **staging and previews**: not set up. When needed, give staging its own Neon branch with URLs in Vercel's Preview environment scoped to mem's staging branch, and remove it from `git.deploymentEnabled` in `vercel.json`.

```sh
neon me                                                   # logged in? otherwise `neon auth`
neon projects list
neon branches list --project-id <id>
neon connection-string dev --project-id <id> --pooled     # DATABASE_URL
neon connection-string dev --project-id <id>              # DATABASE_URL_UNPOOLED
neon psql dev --project-id <id>                           # a SQL shell on the branch
```

Reset the development data by recreating `dev` from `main` (`neon branches reset dev --parent --project-id <id>`), then `bun run db:migrate && bun run db:seed`. Never point `.env.local` at `main`.

For Neon itself (branches, the CLI, connection troubleshooting), see the `neon-postgres` skill.
