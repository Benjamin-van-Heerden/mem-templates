# Next.js Project Guide

This project uses modern Next.js App Router conventions. Do not assume older Next.js behavior from memory. Before writing Next.js code, read the relevant local docs under `node_modules/next/dist/docs/`, especially when touching routing, rendering, caching, auth, or request APIs.

This guide was written from the local `next@16.2.9` docs. If `next` is upgraded, re-check the local docs before making framework-sensitive changes.

## Version-Specific Rules

- Next 16 uses the App Router in `app/` by default.
- Turbopack is the default for both `next dev` and `next build`. Only opt into Webpack with `--webpack` when there is a concrete incompatibility.
- `middleware.ts` is deprecated. Use `proxy.ts` at the project root, or under `src/` if the app uses `src/`.
- Request-time APIs are async. Always `await cookies()`, `headers()`, `draftMode()`, route `params`, and page `searchParams`.
- `params` and `searchParams` props are Promises in pages, layouts, route handlers, and generated metadata/image routes.
- Use generated route helpers where useful: `PageProps<'/route'>`, `LayoutProps<'/route'>`, and `RouteContext<'/route'>`. They are generated by `next dev`, `next build`, or `next typegen`.
- `revalidateTag` requires a second argument such as `'max'` in Next 16. Use `updateTag` in Server Actions for read-your-own-writes behavior.
- `forbidden()` and `unauthorized()` are experimental auth interrupts. They require `experimental.authInterrupts: true` in `next.config.ts` and cannot be called in the root layout.
- React Compiler support is stable but not enabled by default. Do not assume compiler optimizations are active unless `reactCompiler` is configured and `babel-plugin-react-compiler` is installed.

## Project Structure

Common top-level files and folders:

- `app/`: App Router routes, layouts, route handlers, and route-specific UI.
- `public/`: static files served from the site root.
- `next.config.ts`: Next configuration.
- `proxy.ts`: request interception before rendering.
- `instrumentation.ts`: OpenTelemetry/instrumentation hook when needed.
- `.env*`: environment variables. Do not commit secrets.

Inside `app/`, folders define route segments. A folder is not public until it contains `page.tsx` or `route.ts`.

Special files:

- `layout.tsx`: persistent shared UI for a segment.
- `template.tsx`: layout-like wrapper that remounts when its segment changes.
- `page.tsx`: route UI and the leaf of a route subtree.
- `route.ts`: Route Handler for HTTP methods.
- `loading.tsx`: Suspense fallback for page and child segments.
- `error.tsx`: Client Component error boundary for uncaught exceptions.
- `not-found.tsx`: UI rendered by `notFound()`.
- `forbidden.tsx`: UI rendered by `forbidden()` when auth interrupts are enabled.
- `unauthorized.tsx`: UI rendered by `unauthorized()` when auth interrupts are enabled.
- `default.tsx`: fallback for parallel route slots.

Colocate implementation files freely inside `app/` when useful. They are not routable unless exposed by `page.tsx` or `route.ts`. Prefix private folders with `_`, for example `app/dashboard/_components`.

## Configuration

Use `next.config.ts` for project-level configuration:

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typedRoutes: true,
}

export default nextConfig
```

Configuration is executed by Node.js during dev/build/server startup. It is not browser code. Keep it deterministic and small unless there is a clear reason to use phase-specific or async config. `next.config.mjs` is valid for ESM JavaScript, but `.cjs` and `.cts` are not supported config extensions in the local docs.

Use configuration deliberately:

- `typedRoutes: true`: statically type internal `Link` routes in TypeScript projects.
- `reactCompiler: true`: enable React Compiler after installing `babel-plugin-react-compiler`.
- `cacheComponents: true`: opt into Cache Components/PPR and the `use cache` model.
- `experimental.authInterrupts: true`: enable `unauthorized()` and `forbidden()`.
- `turbopack`: configure Turbopack. Use top-level `turbopack`, not old `experimental.turbo`.
- `images`: configure remote image hosts before using remote URLs with `next/image`.
- `redirects`, `rewrites`, and `headers`: static routing and response rules that run before Proxy/filesystem routes according to the documented order.
- `experimental.serverActions.bodySizeLimit`: increase Server Action payload limit only when needed. The default is intentionally small.
- `experimental.serverActions.allowedOrigins`: add trusted origins only when Server Actions must be invoked through a proxy or alternate host.
- `env`: avoid for secrets. Only `NEXT_PUBLIC_` variables are exposed to the browser, but secrets should still be accessed from server-only modules rather than spread through config.
- `output`, `basePath`, `assetPrefix`, `trailingSlash`, `transpilePackages`, and `serverExternalPackages`: deployment/integration settings; add only for a specific deployment or package need.

Route segment config is separate from `next.config.ts`. Pages, layouts, and route handlers can export segment options such as:

```ts
export const dynamic = 'auto'
export const dynamicParams = true
export const revalidate = false
export const fetchCache = 'auto'
export const runtime = 'nodejs'
export const preferredRegion = 'auto'
```

Use segment config sparingly. Prefer local data/cache choices first. Segment config applies across a route tree and incompatible parent/child choices can create confusing behavior.

## Routing

Static routes map directly from folders:

```text
app/page.tsx -> /
app/dashboard/page.tsx -> /dashboard
app/dashboard/settings/page.tsx -> /dashboard/settings
```

Dynamic segments use brackets:

```text
app/blog/[slug]/page.tsx -> /blog/my-post
app/shop/[...slug]/page.tsx -> /shop/a, /shop/a/b
app/docs/[[...slug]]/page.tsx -> /docs, /docs/a, /docs/a/b
```

In Server Components:

```tsx
export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
  const searchParams = await props.searchParams
  return <article>{slug}</article>
}
```

In Client Components, use React `use()` for prop promises or the navigation hooks:

```tsx
'use client'

import { use } from 'react'

export default function Page({ params }: PageProps<'/blog/[slug]'>) {
  const { slug } = use(params)
  return <article>{slug}</article>
}
```

Use `generateStaticParams()` when dynamic routes can be prerendered from known data. It runs before pages/layouts during build and returns an array of params objects. Use `dynamicParams` when you need to control behavior for params not generated at build time.

## Layouts, Templates, and Route Groups

The root layout is required and must render `<html>` and `<body>`. Do not manually add `<head>` tags; use the Metadata API.

Layouts:

- Persist across client navigation.
- Preserve state and remain interactive.
- Do not rerender on every navigation.
- Cannot safely read fresh `pathname` or `searchParams`; use a Client Component with `usePathname()` or `useSearchParams()` for that.
- Can read `params`, but `params` is async.

Templates:

- Sit between a layout and its children.
- Remount when their segment key changes.
- Reset child Client Component state on navigation.
- Are the correct tool when an area needs per-navigation reset behavior.

Route groups use parentheses and are omitted from the URL:

```text
app/(marketing)/page.tsx -> /
app/(app)/dashboard/page.tsx -> /dashboard
app/(admin)/admin/page.tsx -> /admin
```

Use route groups to organize routes, share layouts across selected routes, or create multiple root layouts.

Important layout switching caveats:

- If `app/layout.tsx` exists, it wraps everything. Group-level layouts are nested under it.
- To create completely separate root layouts, omit the top-level `app/layout.tsx` and put root layouts in groups such as `app/(marketing)/layout.tsx` and `app/(app)/layout.tsx`.
- Navigating across different root layouts triggers a full page load.
- Route groups do not protect routes and do not create URL prefixes. `(admin)` is not `/admin`; use an actual `admin` folder when the URL should be `/admin`.
- Two route groups must not resolve to the same URL path, for example `(marketing)/about/page.tsx` and `(app)/about/page.tsx`.

## Server and Client Components

Pages and layouts are Server Components by default. Keep components server-side unless they need client-only capabilities.

Use Client Components only for:

- React state and event handlers.
- `useEffect` and lifecycle logic.
- Browser APIs such as `window`, `document`, `localStorage`, or geolocation.
- Client hooks such as `useRouter`, `usePathname`, `useSearchParams`, and custom hooks that use client features.

Add `'use client'` at the top of the smallest file that needs it. Everything imported by that file becomes part of the client module graph, so do not mark large layouts or broad component trees as client components just for one interactive widget.

Server Components can:

- Fetch data directly.
- Access databases, internal APIs, and secrets.
- Reduce client JavaScript.
- Pass serializable props to Client Components.

Client Components cannot import server-only modules. Mark server-only data modules with:

```ts
import 'server-only'
```

It is valid to pass Server Components as `children` or props into a Client Component. This lets a client shell, such as a modal, display server-rendered content without pulling that content into the client bundle.

## React Compiler and Memoization

React Compiler can automatically optimize component rendering and reduce the need for manual `memo`, `useMemo`, and `useCallback`. In Next 16, the `reactCompiler` config is stable, but it is off by default and requires the compiler plugin:

```bash
npm install -D babel-plugin-react-compiler
```

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  reactCompiler: true,
}

export default nextConfig
```

When enabled, Next uses an SWC optimization to run the Babel-based React Compiler only on relevant files, such as files with JSX or React Hooks. This keeps the compiler from running over the entire project.

Practical guidance:

- Do not add `React.memo`, `useMemo`, or `useCallback` by habit.
- Prefer simple, pure components and normal local functions first.
- Let the compiler handle routine render optimization when it is enabled.
- Keep following the Rules of React. The compiler depends on render purity and valid hook usage.
- Do not rely on memoization for correctness. Memoization is an optimization, not state management.
- Keep `useMemo` for genuinely expensive calculations when profiling shows value, or when a third-party API specifically requires stable object/function identity.
- Keep `useCallback` when stable identity is part of an external contract, for example subscription cleanup or imperative library interop.
- Use `"use no memo"` to opt out a component or hook if the compiler creates a concrete problem.
- Annotation mode is available with `reactCompiler: { compilationMode: 'annotation' }`; then add `"use memo"` inside specific components/hooks to opt in.

Because this repo does not currently enable `reactCompiler`, future agents should not remove existing memoization solely on the assumption that the compiler is active. If enabling it, do it as a deliberate config/dependency change and verify the affected UI.

## Data Fetching and Rendering

Fetch data in Server Components by default. Use Client Component data fetching only for browser-local data, highly interactive client state, or when a client-side cache library such as SWR or React Query is intentionally chosen.

Important rendering facts:

- Next renders Server Components on the server and sends an RSC payload to the client.
- Initial loads use HTML for fast preview, then hydrate Client Components.
- Subsequent navigations use prefetched/cached RSC payloads and client transitions.
- `fetch` requests are memoized within a React render tree, so colocated fetching is acceptable.
- `fetch` is not cached by default in the current model.
- Runtime APIs such as `cookies()`, `headers()`, `searchParams`, and unsampled dynamic `params` require request-time data.

Prefer streaming over blocking a whole route:

- Use `loading.tsx` for route-level fallback UI.
- Use local `<Suspense>` boundaries around slow or request-time sections.
- Keep meaningful static shell content outside Suspense where possible.
- If a layout reads uncached/runtime data, `loading.tsx` in the same segment will not cover it. Move that work to the page or wrap the layout's dynamic section in its own `<Suspense>`.

With Cache Components enabled via `cacheComponents: true`, Next uses Partial Prerendering. Static shell content, cached functions, and streamed runtime content can coexist on the same page.

```tsx
import { cacheLife, cacheTag } from 'next/cache'

export async function getProducts() {
  'use cache'
  cacheLife('hours')
  cacheTag('products')
  return db.query.products.findMany()
}
```

If `cacheComponents` is not enabled, use the previous caching model:

- `fetch(url, { cache: 'force-cache' })`
- `fetch(url, { next: { revalidate: 3600, tags: ['products'] } })`
- `unstable_cache()` for non-fetch work
- route segment config such as `dynamic`, `revalidate`, and `fetchCache` where needed

Prefer tag-based revalidation when possible:

- `revalidateTag('products', 'max')`: stale-while-revalidate, usable in Server Actions and Route Handlers.
- `updateTag('products')`: immediate expiration/read-your-own-writes, Server Actions only.
- `revalidatePath('/products')`: broader path invalidation when tags are not practical.

## Navigation

Use `next/link` for internal navigation. It enables client transitions and prefetching. Plain `<a>` causes full document navigation.

Dynamic routes can feel slow if there is no prefetched fallback. Add `loading.tsx` to dynamic route segments or local Suspense boundaries around request-time work.

With Cache Components, routes that must navigate instantly should export `unstable_instant` and satisfy its validation:

```tsx
export const unstable_instant = { prefetch: 'static' }
```

This catches misplaced Suspense boundaries or uncached data that would block client navigation. Use it for important flows rather than everywhere by default.

## Request APIs

Always use request APIs asynchronously:

```tsx
import { cookies, headers } from 'next/headers'

export default async function Page() {
  const cookieStore = await cookies()
  const headerStore = await headers()
  const theme = cookieStore.get('theme')?.value
  const userAgent = headerStore.get('user-agent')
  return <main>{theme ?? userAgent}</main>
}
```

Cookie rules:

- Reading cookies works in Server Components.
- Setting and deleting cookies only works in Server Functions/Actions or Route Handlers.
- HTTP cannot set cookies after streaming starts.
- Use `httpOnly`, `secure`, `sameSite`, `expires`/`maxAge`, and `path` deliberately for auth/session cookies.

`searchParams` is only available as a prop on pages. Layouts do not rerender on navigation, so putting query-dependent logic in layouts creates stale state.

## Server Actions and Mutations

Server Functions are async functions marked with `'use server'`. When used for forms or mutations, they are Server Actions.

Security rule: treat every Server Action as a public POST endpoint. It can be invoked directly, not only through the UI.

Always in Server Actions:

- Validate input from `FormData`, params, cookies, and headers.
- Verify authentication and authorization inside the action.
- Perform mutations on the server.
- Revalidate affected caches with `updateTag`, `revalidateTag`, or `revalidatePath`.
- Use `redirect()` after successful mutations when appropriate, outside `try/catch`.

Expected validation errors should usually be return values consumed by `useActionState`, not thrown exceptions. Throw unexpected errors for bugs and infrastructure failures.

## Route Handlers and API Endpoints

Use `route.ts` for custom HTTP endpoints that do not render React components. This is the App Router equivalent of API routes for new code.

```text
app/api/health/route.ts -> /api/health
app/api/users/[id]/route.ts -> /api/users/:id
app/webhook/route.ts -> /webhook
app/rss.xml/route.ts -> /rss.xml
```

Route Handlers use standard Web `Request` and `Response` APIs, plus optional `NextRequest`/`NextResponse` helpers. They can return JSON, text, XML, streams, files, redirects, empty statuses, or any other HTTP response body. They do not return JSX and do not participate in the React layout tree.

Supported method exports are `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, and `OPTIONS`. If `OPTIONS` is not defined, Next automatically implements it and sets the `Allow` header based on the exported methods.

```ts
import type { NextRequest } from 'next/server'

export async function GET(_request: NextRequest, ctx: RouteContext<'/api/users/[id]'>) {
  const { id } = await ctx.params
  return Response.json({ id })
}
```

Use `RouteContext<'/literal'>` for typed dynamic params. `ctx.params` is a Promise.

Reading request data:

```ts
import type { NextRequest } from 'next/server'

export async function POST(request: NextRequest) {
  const contentType = request.headers.get('content-type')
  const search = request.nextUrl.searchParams.get('q')
  const body = contentType?.includes('application/json')
    ? await request.json()
    : await request.text()

  return Response.json({ search, body })
}
```

Rules for request bodies:

- `GET` and `HEAD` requests do not carry a body.
- Read the body with `request.json()`, `request.formData()`, `request.text()`, `request.arrayBuffer()`, or stream APIs.
- A request body can only be read once. Use `request.clone()` if two independent consumers must read it.
- Validate all body, query, header, cookie, and path param values before using them.
- Do not echo detailed internal errors to clients.

For webhooks, use Route Handlers and usually read the raw body with `request.text()` or `request.arrayBuffer()` so signature verification receives the exact payload:

```ts
import { NextResponse, type NextRequest } from 'next/server'

export async function POST(request: NextRequest) {
  const signature = request.headers.get('x-signature')
  const rawBody = await request.text()

  if (!signature || !verifyWebhookSignature(rawBody, signature)) {
    return NextResponse.json({ ok: false }, { status: 401 })
  }

  const event = JSON.parse(rawBody)
  await handleWebhookEvent(event)

  return NextResponse.json({ ok: true })
}
```

Unlike Pages Router API Routes, App Router Route Handlers do not need `bodyParser` configuration for webhooks.

For callback URLs, Route Handlers can verify the incoming request, set cookies, and redirect:

```ts
import { NextResponse, type NextRequest } from 'next/server'

export async function GET(request: NextRequest) {
  const token = request.nextUrl.searchParams.get('session_token')
  const redirectTo = request.nextUrl.searchParams.get('redirect_url') ?? '/'

  if (!token || !isAllowedRedirect(redirectTo)) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  const response = NextResponse.redirect(new URL(redirectTo, request.url))
  response.cookies.set({
    name: 'session',
    value: token,
    httpOnly: true,
    secure: true,
    sameSite: 'lax',
    path: '/',
  })

  return response
}
```

For CORS, either set headers in the specific Route Handler, use Proxy for shared logic, or use `headers()` in `next.config.ts` for static header rules. Define `OPTIONS` yourself when you need custom preflight behavior.

Caching and runtime notes:

- Do not assume `GET` Route Handlers are statically cached. In the current docs, the default GET handler caching changed from static to dynamic in v15.
- Use segment config (`revalidate`, `dynamic`, `fetchCache`, `runtime`, etc.) or Cache Components patterns deliberately when a handler should cache.
- Route Handlers can use `generateStaticParams()` for dynamic params when responses can be generated ahead of time.
- Route Handlers can stream responses with Web `ReadableStream`.
- Route Handlers can call `revalidateTag`, `revalidatePath`, and `redirect` where appropriate.

Security rules:

- Route Handlers are public endpoints. Verify auth and authorization inside each handler.
- Do not rely on UI hiding or Proxy checks alone.
- Keep secrets server-side. Do not return tokens or raw provider payloads unless explicitly intended.
- Consider rate limiting for mutation-heavy, webhook, auth, and public POST endpoints.
- Validate content type and body size before expensive processing.
- For webhooks, verify signatures/timestamps and make handlers idempotent because providers commonly retry.

## Proxy, Auth, and Route Isolation

Next 16 calls middleware "Proxy". Use `proxy.ts`, not `middleware.ts`.

Proxy runs before routes render. It can redirect, rewrite, modify headers/cookies, or return a response. It is useful for fast request-level routing and optimistic auth checks. It is not a full authorization layer.

Proxy rules:

- Keep it fast. Do not perform slow database reads.
- Use cookies or cheap token/session decoding for optimistic decisions.
- Use a constant `matcher`; dynamic matcher values are ignored.
- Exclude static assets and image optimization when appropriate.
- Only one `proxy.ts` file is supported. Split logic into helper modules and import them.
- `fetch` cache options have no effect in Proxy.
- Server Actions are POST requests to the route where they are used. If the Proxy matcher excludes that path, Proxy will not cover the action. Actions must still verify auth internally.

Recommended cross-pollination pattern:

1. Give protected areas stable URL prefixes, for example `/admin`, `/student`, `/provider`, `/dashboard`.
2. Use route groups only for layout organization, not protection.
3. In `proxy.ts`, use cookie/session claims for optimistic redirects so users do not enter the wrong area.
4. In the DAL, pages, Server Actions, and Route Handlers, re-check the real session and role close to the data or mutation.
5. For a user with the wrong role, redirect to that user's home area or render/return 403. Do not show the other role's UI and rely on hiding buttons.

Example Proxy shape:

```ts
import { NextResponse, type NextRequest } from 'next/server'

type Role = 'admin' | 'student' | 'provider'

const routePolicies: Array<{ prefix: string; roles: Role[] }> = [
  { prefix: '/admin', roles: ['admin'] },
  { prefix: '/student', roles: ['student'] },
  { prefix: '/provider', roles: ['provider'] },
]

function homeFor(role: Role) {
  if (role === 'admin') return '/admin'
  if (role === 'student') return '/student'
  return '/provider'
}

export async function proxy(request: NextRequest) {
  const path = request.nextUrl.pathname
  const policy = routePolicies.find((item) => path === item.prefix || path.startsWith(`${item.prefix}/`))

  if (!policy) {
    return NextResponse.next()
  }

  const token = request.cookies.get('session')?.value
  const session = token ? await decryptSessionClaims(token) : null

  if (!session) {
    const loginUrl = new URL('/login', request.url)
    loginUrl.searchParams.set('next', path)
    return NextResponse.redirect(loginUrl)
  }

  if (!policy.roles.includes(session.role)) {
    return NextResponse.redirect(new URL(homeFor(session.role), request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico|.*\\.(?:png|jpg|jpeg|gif|svg|webp|ico)$).*)'],
}
```

That example is intentionally optimistic. The secure check belongs in server-only code:

```ts
import 'server-only'

import { cache } from 'react'
import { cookies } from 'next/headers'
import { forbidden, unauthorized } from 'next/navigation'

type Role = 'admin' | 'student' | 'provider'

export const verifySession = cache(async () => {
  const token = (await cookies()).get('session')?.value
  const session = token ? await loadAndValidateSession(token) : null

  if (!session) {
    unauthorized()
  }

  return session
})

export async function requireRole(...roles: Role[]) {
  const session = await verifySession()

  if (!roles.includes(session.role)) {
    forbidden()
  }

  return session
}
```

If `authInterrupts` is not enabled, use `redirect('/login')`, `notFound()`, or explicit `Response` statuses instead of `unauthorized()`/`forbidden()`.

Do not put the only auth check in a layout. Layouts do not rerender on every navigation. Auth checks should happen in the DAL, page, leaf Server Component, Server Action, or Route Handler that actually accesses protected data or performs a protected mutation.

## Data Security

Prefer a Data Access Layer for new application code:

- Mark it with `import 'server-only'`.
- Read secrets and environment variables only in server-only modules.
- Verify authentication and authorization there.
- Return minimal DTOs rather than full database records.
- Use React `cache()` to deduplicate per-request session and data lookups.

Do not pass raw database rows, session objects, password hashes, tokens, permissions maps, or broad user objects into Client Components. Client Component props are part of the client data boundary and must be treated as public.

Only environment variables prefixed with `NEXT_PUBLIC_` are exposed to the browser. Never put secrets under that prefix.

## Error Handling and Redirects

Expected errors:

- Model validation and normal business failures as return values.
- Use `useActionState` for form error display.
- Return explicit `Response` status codes in Route Handlers.

Unexpected errors:

- Throw and let `error.tsx` catch them.
- `error.tsx` must be a Client Component.
- Use the `unstable_retry` prop to retry a failed segment when appropriate.

Use:

- `notFound()` plus `not-found.tsx` for 404s.
- `redirect()` for navigation redirects.
- `permanentRedirect()` for 308 permanent redirects.
- `unauthorized()`/`forbidden()` only with `experimental.authInterrupts: true`.

`redirect()` throws internally and should be called outside `try/catch`. In Server Actions it returns a 303; otherwise it usually returns a 307. In a streaming context, redirects and not-found states may be communicated inside the streamed response after headers have already been sent, so the HTTP status may remain 200. If a real 404/403/401 status is required for compliance or analytics, decide before streaming starts.

## Metadata, Images, Fonts, and CSS

Use the Metadata API instead of manual `<head>` tags:

```tsx
import type { Metadata } from 'next'

export const metadata: Metadata = {
  title: 'Studii',
  description: '...',
}
```

Use `generateMetadata()` for route metadata that depends on data. Its `params` and `searchParams` are async in App Router pages. Metadata exports are Server Component only.

Special metadata files include `favicon.ico`, `icon.*`, `apple-icon.*`, `opengraph-image.*`, `twitter-image.*`, `robots.txt`, and `sitemap.xml`. More specific files deeper in the route tree override broader ones.

Use `next/image` for optimized images. Configure remote image hosts in `next.config.ts` before using remote URLs. Static assets under `public/` are referenced from `/`, for example `/logo.svg`.

Use `next/font` from layouts for local or Google fonts. It avoids layout shift and keeps font loading integrated with rendering.

Global CSS belongs in the root layout import path, typically `app/globals.css`. Keep component-specific styles close to the component when the chosen styling approach supports it.

## Practical Defaults for This Project

- Prefer App Router. Do not add `pages/` unless there is a specific compatibility reason.
- Keep most components as Server Components.
- Add `'use client'` only at small interactive boundaries.
- Put shared server data access under a server-only DAL.
- Use route groups for layout organization, not authorization.
- Use explicit URL prefixes for role-protected app areas.
- Use `proxy.ts` for cheap, optimistic redirects only.
- Re-check auth and role inside every protected page data load, Server Action, and Route Handler.
- Use `loading.tsx` and Suspense around dynamic/slow sections.
- Use `PageProps`, `LayoutProps`, and `RouteContext` for typed async route params.
- If enabling `cacheComponents`, use `use cache`, `cacheLife`, `cacheTag`, and local Suspense boundaries deliberately.
- If not enabling `cacheComponents`, use the previous caching APIs deliberately and document why.
